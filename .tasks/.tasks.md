That refusal is right (the alternative was writing an empty state over their real blobs, which is the bug it was added for) and it was completely invisible. `lib/hydration-gate-notice.ts` is the missing half.

  **The latch is module-level, not per-provider, because the cause is a DEVICE.** A store that cannot be read fails every provider that reads it, so five toasts saying the same sentence is worse than one. Same shape as `lowProfileCacheTtlWarningShown` in `social-context` and for the same reason: it has to survive a Strict-Mode double-mount and any provider remount, which a `useRef` cannot. It is deliberately not cleared on sign-out — the device is still broken for the next account.

  **Each provider passes its own predicate, and that is the part a shared hook could have got wrong.** `premium-context` sets `ready` TRUE on the signed-out path with the gate shut, so a derived `ready && !safe` would have toasted at every launch of a signed-out app. The four user-scoped providers pass `&& !!user` (or `&& !!storageKey`); `marketplace-context` has one global key and no account at all.

  **Ten cases, seven of them about when and how many.** One toast for two providers refusing at once; none while the gate is open; one when a gate closes AFTER the first render, which is when a hydrate actually resolves; none repeated across a second mount. `error` rather than `info`, because the session is losing data.
