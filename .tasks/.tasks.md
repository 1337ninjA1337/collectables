## The collection remembers how you like to read it (2026-09-10)

<!-- Fifth bullet of "SORT_OPTIONS + sort chip a11y" (2026-08-07): "Persist the chosen sort per collection". -->

- [DONE: 2026-09-10] [est: 18000] **`useItemSortPref` — the sort survives leaving the screen, and nothing else does** — `itemFilters` reset to `EMPTY_FILTERS` on every mount, so a user who prefers A→Z re-picked it on every visit, two taps behind a sheet. Only the sort persists: a query or a tag filter is the question the user is asking right now, and restoring one would hide items with no visible cause.

  **Per collection, keyed by id in one blob** (`collectables-item-sort-v1`). The choice does not generalise — the cost sort means nothing in a collection whose items carry no prices — and one blob is one read per open instead of a key per collection.

  **`"default"` deletes the entry.** "I cleared it" and "I never picked one" behave identically, so they are one state; storing the default would grow the blob for every sheet the user opened and backed out of.

  **A retired mode is dropped on read.** The blob outlives the build that wrote it, and a mode no longer in `SORT_OPTIONS` would sort nothing while showing no chip — a picker that looks broken. Validated against `SORT_OPTIONS` itself, so a mode retires from storage the moment it retires from the UI; one bad entry costs that collection's sort, never the whole blob.

  **Applied once, and never over the user's own pick** — the read is async, so a sort chosen while it was in flight would otherwise be replaced by the stored one.

  **Related bug found and fixed:** the reorder notice's "reset sort" only changed local state, so the sort the user just turned off came back on the next visit. All three surfaces that can change the sort now remember it.

## A reorder writes a dense run over the WHOLE collection (2026-09-10)

<!-- Second bullet of "After the collection-order extraction" (2026-08-28): "Give `reorderItemsInCollection` a duplicate-index assertion of its own". -->

- [DONE: 2026-09-10] [est: 15000] **`planItemReorder` — the writer refuses to persist a run with holes** — `reorderItemsInCollection` renumbered only the ids it was handed, so an `orderedIds` that misses part of the collection left the rest holding their old indices, which collide with the freshly-written ones. `byCollectionOrder`'s id tiebreak renders that deterministically, which is damage control, not prevention: the collision stays in storage and the next reorder writes on top of a run that already has duplicates. The planner lays the collection's items out as a dense 0..N-1 permutation — named ids first in the order given, the rest after in their rendered order — so a partial call cannot be persisted badly.

  **The id list is a request, not gospel.** An id naming no member of the collection is skipped rather than consuming an index (it would push every real row down one), and a repeated id counts once, at its first appearance. Items in other collections keep both their number and their place in the array.

  **Only what moved gets written.** `changed` holds the rows whose number actually differs, so the drag that ends where it started syncs nothing and the plan returns `items` by reference — the same no-op contract `mergeItemsFromCloud` states, so the caller skips the `setState` and the AsyncStorage rewrite behind it.

  **Related bug found and fixed:** both reorders collected their sync list by pushing into a closure array from INSIDE a `setState` updater, then read it synchronously on the next line. React runs that updater when it renders, not when the setter is called, so the cloud write could be skipped entirely (or, under StrictMode's double-invoke, sent twice). Both now decide from the state this render is holding.

## Which row the user actually picked (2026-09-10)

<!-- First bullet of "Fresh-read follow-ups" (2026-09-10): "`index` is still the render's answer while `rows` is now the action's". -->

- [DONE: 2026-09-10] [est: 14000] **`identify` — the row is found by id at action time, not assumed to be where it was drawn** — reading the rows fresh was half a fix. Re-checking whether a move EXISTS at the old index says nothing about whether the row is still sitting there: a cloud merge that reorders the list leaves the index pointing at a different card, so the user asks to move Alpha and Beta moves. Silent, and correct as far as every other check is concerned — the commit is a well-formed whole-list order, it just reorders the wrong thing.

  **By key, not by reference.** A merge rebuilds the objects: the same collection comes back as a new object with the same id, so `indexOf` would find nothing and the action would do nothing on every merge. `identify: { row, keyOf }` and a `findIndex` over the key is what survives that.

  **A row the key cannot find has LEFT the list** — deleted, filtered out, moved to another collection — and the action does nothing. Falling back to the render's index is the one thing that must not happen there, because it is exactly the bug this closes.

  **Optional, and the default is the old behaviour.** A caller whose list cannot be reordered underneath it passes nothing and keeps the render's index; a case pins that, so the fallback is a decision rather than an accident.
