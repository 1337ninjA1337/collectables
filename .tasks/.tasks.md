## The harness had no unmount phase (2026-08-30)

- [DONE: 2026-08-30] [est: 24000] **`render()` grew an unmount phase, so "does this component clean up after itself?" is finally a question a case can ask** — effect cleanups ran only when a dep changed, which meant a probe dropped from the tree kept its instance, its state AND its subscription. Every suite that cared about a teardown worked around it by calling the subscription API by hand and asserting on the registry, which tests the registry rather than the component: the storage-notice unsubscribe case said so in its own comment.

  **The instance map now knows what the pass did NOT render.** `runComponent` records each key it visits, and the sweep after the walk tears down every instance missing from that set — child before parent, which is reverse insertion order and the order React destroys a deletion in. So a closed conditional branch is an unmount now: its effects clean up, and a re-added branch gets fresh state instead of the state it had before it disappeared.

  **`tree.unmount()` is the whole-tree form.** Idempotent, and `rerender`/`press` throw afterwards with a message that says why rather than a `TypeError` three frames down.

  **Cleanups are found through a per-instance `effectCells` set rather than by type.** An effect stores its cleanup in its own hook cell, and `useCallback` stores a function in one too — "every cell holding a function" would have called a memoised press handler as a destructor.

  **Nine new cases: seven on the harness contract, two on the notice.** The storage-notice unsubscribe case is now a real unmount (`observer count 1 → 0`, and a write reported afterwards raises nothing), and the hand-rolled registry version it replaces is gone. On the harness: teardown order, idempotence, the refusal to re-render, the closed branch, fresh state for a re-added one, an effect that returns no cleanup, and the dep-change re-subscribe that pins the existing behaviour the sweep must not disturb.

## One listener for a registry that reaches the whole tree (2026-08-30)

<!-- First bullet of "Storage-notice follow-ups", filed the run before: "five providers each mount their own observer and the registry now holds five entries doing the same work ... one `<StorageNotice />` beside `ToastProvider` in `app/_layout.tsx` would subscribe once". The trade it named — the gate half would need the flag out of five context values — is the one this did NOT take: the gate half stays where it is. -->

- [DONE: 2026-08-30] [est: 21000] **The write half of the storage notice subscribes once, from the app shell, instead of five times from the providers** — `useStorageNotice` did two jobs with two different multiplicities: a per-provider gate predicate, and a subscription to a MODULE-LEVEL registry that already carries every failing write in the tree. The second one needs one listener; it had five, and the latch made the extra four invisible from every assertion about what the user sees.

  **`useStorageFailureNotice()` is the split, and `components/storage-notice.tsx` is its only caller.** It renders `null` and is mounted directly under `ToastProvider` in `app/_layout.tsx` — ABOVE the auth gate on purpose, because the providers below it unmount around a sign-out and an account switch, and a store that fills up during one is exactly when the user needs telling. Both hooks raise through the same module-level latch, so a device that fails both ways still says it once.

  **The cost of the split is stated in a case rather than discovered later.** A provider that reports a rejected write now reaches nobody unless the listener is mounted, so the mount IS the adoption requirement: four cases hold it — exactly one module in the tree calls the hook, `app/_layout.tsx` renders `<StorageNotice />`, the tag sits between `<ToastProvider>` and its close, and it sits above `<AuthProvider>`.

  **`__storageFailureObserverCountForTests` exists because the outcome cannot see this.** Five subscribers and one subscriber raise the same single toast; the difference is five closures and five `Set` entries. The new cases assert the COUNT: two gated probes add zero observers, the listener adds exactly one, and a re-render does not add a second.

  **`mountStorageNoticeListener()` in the shared mount harness keeps the end-to-end fact end-to-end.** `premium-provider-mounted` asserted that a rejected `setItem` reaches the user; that assertion now mounts the shell's listener beside the provider — and so does its silent twin, which would otherwise pass because nobody was listening rather than because the session was healthy.
